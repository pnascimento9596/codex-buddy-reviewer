## PR #27 disposition — actions/attest 4.2.0 → 4.2.1

**Decision: merged** through protected CI as `19c8e8923b1b76d82f45cba63dbff3f94308a601` before further RC prep.

**Diagnosis (reproduced 2026-08-06):**

- Diff is a single pin change in `.github/workflows/release.yml` attest job:
  `actions/attest@f7c74d28… # v4.2.0` → `actions/attest@508db95d… # v4.2.1`.
- Workflow subjects are local files (tarball, distribution bundle, distribution
  JSON) via `subject-path`. Post-attest verification uses
  `gh attestation verify` with `--repo`, `--signer-workflow`, `--source-digest`,
  `--source-ref`, and `--deny-self-hosted-runners`.
- Upstream v4.2.1 notes (2026-07-29): tar 7.5.17→7.5.21; fix strip OCI image tag
  when pushing attestation to a registry; dependency bumps. No documented change
  to GitHub Actions attestation predicate content, subject binding for file
  subjects, or signer identity fields this workflow re-verifies.
- Repository verification steps remain `gh attestation verify` on the three
  subjects; they do not depend on OCI registry push behavior.

**Reason to merge rather than defer:** leaving an open Dependabot PR that changes
the attestation-minting action through a release is undeclared drift. Merging
after green protected CI makes the next release's attestations come from a
CI-verified current pin. Deferred same-as-rc.4 pin would also have been
defensible; undecided was not.

## Security-scan gate (rewritten)

### Diagnosis (confirmed against repository, 2026-08-06 at `71d6c34`)

1. **Artifact path inventory** (empirical `npm run release:build` /
   `release:verify` at source `71d6c34`; `file_count` 130 manifest files +
   `release-manifest.json` = **131 paths**):

   Generated/transformed always: `package.json`, `.codex-plugin/plugin.json`,
   `assets/pets/catalog.json`, `release-manifest.json`.
   Plus allowlisted trees (`evals/`, `hooks/`, `native/`, `schemas/`, `skills/`,
   `src/`), pet packages, selected scripts, selected docs.

   **`docs/VALIDATION.md` is in the artifact. `docs/releases/` is not.**

2. Classification of the 131-path inventory: runtime code (src/scripts/hooks/
   native/skills), evals corpus, schemas, assets (pets), documentation
   (including VALIDATION.md), version-bearing manifests.

3. Pre-dispatch ritual (rc.4 and earlier): write a dispatch-attribution statement
   into `docs/VALIDATION.md` immediately before firing the release workflow
   (see rc.4 release note checklist and Layer A text).

4. **Structural impossibility under the old wording:** if attribution must be
   committed into an in-artifact path, the exact head that ships is one commit
   newer than any head that can be sealed and scanned without that commit. The
   gate text "re-run the exact-head scan on the final promotion head" could never
   close without either (a) scanning after the attribution commit (and then
   needing another attribution commit), or (b) shipping without the ritual
   commit. Confirmed against actual file membership.

### Resolution chosen

**Resolution A (structural) + Resolution B (residual version rule).**

- **A:** Move new dispatch-attribution statements to
  `docs/releases/dispatch-attribution.md` (out of artifact). Keep historical
  attribution already inside `docs/VALIDATION.md`. Point VALIDATION.md at the
  new home without deleting history.
- **B:** Even with A, an RC/stable version bump still changes `package.json` and
  `.codex-plugin/plugin.json` inside the artifact. Define the scan surface and
  the only post-scan deltas that do not re-open the gate.

### Newly permitted post-scan delta classes (explicit)

These classes would previously have forced "final head ≠ scanned head" under the
old exact-head wording, and are now permitted **only** under the allowlist and
a disposition entry in `docs/releases/dispatch-attribution.md` (not in this
readiness ledger):

1. Out-of-artifact `docs/releases/dispatch-attribution.md` updates under the
   two-phase protocol (no self-referential future SHA), including post-scan
   disposition entries (path + diff digest + reviewer sign-off).
2. Identity-only `docs/releases/v0.5.0-rc.*.md` candidate notes (not the stable
   readiness / gate ledger).
3. Out-of-artifact governance checklist edits under `docs/GOVERNANCE-TODO.md`.
4. Pure version-identity RC/stable prep bump **fallback only** when the
   intended order (version-prep → seal/scan → dispatch same head) cannot be
   held: package/plugin/lock version fields and version-string-only test
   assertion updates, each with a dispositioned entry in
   `docs/releases/dispatch-attribution.md`. README.md / CHANGELOG.md /
   docs/VALIDATION.md label renames are **not** newly permitted.

**Not** newly permitted: edits to `docs/releases/v0.5.0-stable-readiness.md` or
any other gate/disposition document — those remain on the scan surface.
Writing the mandatory post-scan disposition entry into this file would re-open
the gate it claims to disposition; that entry belongs only in
`docs/releases/dispatch-attribution.md`.

Everything else that used to require a re-scan still requires a re-scan. The
scan surface is not smaller than the prior whole-tree sealed partitions for
runtime, tests, and security-relevant docs; it removes only the impossible
self-reference created by writing attribution into an in-artifact path and the
pure version-identity fields that every RC prep must change.
